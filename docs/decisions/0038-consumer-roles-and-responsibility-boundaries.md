# ADR-0038: 消费方角色命名与职责边界成文

## 状态

**Accepted（2026-08-13）。** 本 ADR 关闭审计 [0081/V386–V390](../audit/archived/0081-2026-08-13-review.md) 的下游
消费边界缺口。全部改动为**文档修订**：不修改 Schema、组件 DSL 或 conformance fixtures，既有合法输入的
默认值与可观测结果不变，按 PATCH 修订发布（2.8.2）。

## 背景

审计 0081 对核心规范做下游消费边界审计，结论是边界机制总体成熟（权威层级、capability 门控、边界条款、
职责归属语句四重机制），但存在一个结构性缺口：协议从未给消费方角色命名，"后端"一词至少三重指代——

- **页面生产方**（写 YAML、跑 CI）：`00` §1、`06` §1"后端 CI / 提交前"；
- **业务 API 实现方**（实现页面引用的 HTTP API、负责鉴权与幂等去重）：`04` §5、`07` §3；
- **manifest 生产方**（提供 app-manifest，内容却含前端路由模板）：`09` §2。

下游按角色拆分（A 团队写页面、B 团队实现 API）时，"`04` 的契约约束 A 还是 B"没有协议文本可查。
附带问题：`00` 术语表无任何角色条目；校验执行点不唯一（`06` v0.2.4 变更）；权限行为表用 DOM 词汇；
错误文案的 Host 边界前后不一致；`01` 残留 "2.7" 版本。

## 决策

### D1. 六个消费方角色进入 `00` 术语表（权威定义）

| 角色 | 定义 |
|---|---|
| **页面生产方** | 编写页面 YAML/JSON（Node 树、`datasources`、`actions`、`meta` 声明）并承担生产方 CI 校验的一方；可以是后端团队、独立页面团队或 AI 助手 |
| **业务 API 实现方** | 实现页面引用的 HTTP API（DataRef / optionsSource / recordSource / Action / 上传端点），负责鉴权、错误响应结构与幂等去重的一方 |
| **manifest 生产方** | 提供 `app-manifest.json`（及可选的 bootstrap document）的一方 |
| **Renderer** | 前端核心：递归解析 Node 树、按 `type` 分发到组件注册表；实现协议规定的可观测行为 |
| **Host（宿主应用）** | 装配 Renderer、注入 `baseURL` / `$context` / 认证、提供 UI 壳与运行环境的一方；可选择声明 `10` 的可选能力 |
| **组件库/皮肤系统** | 维护 `type` → 具体组件实现映射，决定视觉与交互呈现的一方 |

章程与 README 已有的"后端页面生产方"表述统一为"页面生产方"。

### D2. "后端"用词统一规则

1. 指页面 YAML 生产 → **页面生产方**；指 API/鉴权/幂等 → **业务 API 实现方**；指 manifest → **manifest 生产方**；
2. 泛称"前后端"（charter、README、文档地图）保留；
3. 专名与历史保留：`06` "行级后端请求"、charter "业务后端""后端框架"、场景名"表格行级后端动作"；
4. 完整替换位置清单（本变更集原子执行）：

| 文件 | 位置 | 替换 |
|---|---|---|
| `00` §1 | L16/L19/L83/L84 | 后端 → 页面生产方 |
| `00` §2 文档地图 | `01`/`02`/`03`/`04`/`06`/`07`/`08`/`09`/`migrations` 读者列 | 按 D1 角色改写 |
| `02` | L11/L72/L121 | 后端 → 页面生产方 |
| `02` | L149/L308/L332 | 后端 → 业务 API 实现方 |
| `04` | L3 owner / L10-11 / L51 / L72 / L123 / L195 / L206 / L228 / L232 / L233 / L246 / L250 / L270 / L282 / L284 / L285 | 按指代改为业务 API 实现方（或业务 API） |
| `06` | L14/L15/L16 时机列 | 后端 CI → 页面生产方 CI |
| `06` | L105 标题 / L176 checklist | 后端开发者 → 页面生产方 |
| `07` | L39 | 后端配置 → 页面配置 |
| `07` | L66/L139/L302/L316/L328 | 后端 → 业务 API 实现方（服务端存储系统） |
| `07` | L72/L142 | 后端接口/后端请求 → 业务 API / 服务端请求 |

| `PROJECT_CHARTER` | L51 变更门禁第 3 问 | 改为"页面生产方、业务 API 实现方、Renderer/Host 等各类消费方分别受到什么影响？" |

### D3. `00` 新增 §4.1 职责矩阵

在 §4 协议边界下新增职责矩阵（角色 × 生产/拥有 × 必须遵循 × 自行决定），作为"契约管谁"的总索引。
矩阵内容见 `00` §4.1；后续新增契约条款应沿用该角色词汇。

### D4. 校验执行点唯一化（0081/V388）

- `06` v0.2.4 变更（`responseMapping` 条件必填）：执行点唯一化为 **L2**（与 `03` recordView
  "仅 L2 为权威执行点"的先例一致），并注明职责分配——页面生产方 CI 负责保证，Renderer 加载时兜底；
  不再写"L2、L4 或人工 review"三选一；
- `02` 循环保护："建议 10 轮"改为"实现上限由 Renderer 自定（确定的正整数），建议 10 轮"；
  上限只影响何时进入错误态，不影响既有可观测结果；
- 分级机制（部分规则仅 L2 强制、L3a 在 CI 侧可选）是既有设计特征：L0/L1 由页面生产方 CI 保证，
  L2 为语义执行点，L3a/L3b 由 Renderer 加载时兜底——不再视为缺陷，但文档需写明该职责分配。

### D5. 规范行为去实现细节化（0081/V389）

- `01` §3.9 权限行为表去 DOM 化："节点不应存在于 DOM 中" → "节点不渲染且不参与交互（用户无权限）"；
  "节点渲染为只读/禁用态，而非从 DOM 中移除" → "节点以只读或禁用形态呈现，不提供编辑/操作入口"；
- `04` §6.1/§6.4 错误文案补注边界：表内文案是协议安全兜底**示例文案**（语义稳定、不透出服务端细节），
  最终展示由 Host i18n 体系决定；Host 可用等价语义文案替换，不得改变错误语义与分类。

### D6. 版本残留修复（0081/V390）

- `01` L28/L47："2.7" → "2.8"；
- `02` L178 与 `04` §7、`08` §3 示例中的旧版本文本确认为有意历史示例/版本下限，保留。

### D7. 显式留白标注（0081 次级发现）

对以下三处"协议不规定、由某方自决"的事实补注，不改语义：

- `09` §6 navigate 接缝：未命中注册表时 `$context.route` **不注入**；命中时按 §7 注入——两条路径
  的对照成文；
- `07` §8 `reload`：行级目标为触发表格（既有）；页面级触发入口的 `reload` 目标**本协议不规定**，
  由 Renderer/Host 自决；
- `04` §2 `sort`：wire 格式与状态机由协议规定；排序结果语义（比较规则、后端忽略 `sort` 时的行为）
  由业务 API 实现方自决。

### D8. 版本与交付门禁

纯文档修订：不改 Schema / DSL / fixtures（fixture digest 仍 `7aacf133…`）、不改合法输入与可观测结果，
按 PATCH 修订发布 2.8.2。`protocol-manifest.json` 收录本 ADR（`authority.semanticSpecs`）；MCP 的
decisions 文档经 glob 自动索引（`DOC_MAP` 无需改动）；MCP 与 validator 的捆绑协议版本随制品版本同步。
MUST/SHOULD 效力词汇规范化（0081/V393）、错误文案 messageKey 化（V392）、`text` 默认取值键序
（V391）均**不进入本 ADR**，登记为后续候选。

## 后果

**正面：**

- 下游按角色找契约有权威索引（`00` §3 术语表 + §4.1 职责矩阵），"这条约束管我"有答案；
- "后端"三重指代消除，`04`/`07` 的契约当事方可机械识别；
- 校验执行点唯一，权威与兜底的职责分配成文；
- 规范正文不再锚定 DOM 等实现细节，错误文案边界与 08 §4.2 / 10 §3.6 的 Host 词典化哲学对齐。

**负面 / 取舍：**

- 一次跨 9 个核心文档的措辞修订，diff 面大（但全部为文字替换，无语义变化）；
- 未解决 P3 候选（键序、messageKey 化、效力词汇），需后续 ADR；
- 文档措辞修订无法用 fixtures 机器验证，依赖 `check:links` / `release:check` 与人工评审。
