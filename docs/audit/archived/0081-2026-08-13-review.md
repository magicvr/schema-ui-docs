# 审计报告 0081：下游消费边界审计

## 结论

对核心规范（charter、`00`–`10`、权威 ADR、`conformance/README.md`）做下游消费边界审计：协议对
"哪些遵循协议、哪些下游自决"的边界**总体明确**（四重机制：权威层级/制品清单、边界条款、可执行门控、
职责归属语句），且明确程度随版本递增——v2.8 的 Host/App 互操作层（ADR-0034–0037 / `10`）是边界工程
最成熟的一层。

但发现 **1×P1 + 3×P2 + 4×P3（V386–V393）**，其中 P1 为结构性缺口：协议从未给消费方角色命名，
"后端"一词三重指代（页面生产方 / 业务 API 实现方 / manifest 生产方），下游阅读任何一条契约时的
第一问"这条约束管我吗"没有权威答案。修复方案为新增 ADR-0038（角色命名 + 职责矩阵 + 措辞修订 +
显式留白），全部改动为**文档修订**（不改 Schema/fixtures，合法输入、默认值与可观测结果不变），
按 PATCH 修订入 2.8.2。

本文不是协议权威来源。`docs/audit/**` 不进入 `protocol-manifest.json`、协议制品、MCP 索引或 Docker 镜像。

## 问题详情（V386–V393）

### V386（P1）消费方角色从未命名，"后端"一词三重指代

协议对前端侧角色划分清晰（Renderer / Host / 组件库 / legacy adapter），但生产侧只有"后端"一词，
承载三个不同角色：

- **页面生产方**（写 YAML、跑 CI）：`00:16`"后端定义页面的语义、数据和结构"、`06:14-15`"后端 CI / 提交前"；
- **业务 API 实现方**（实现 `/api/orders`、负责鉴权、Idempotency-Key 去重）：`04:206`"后端必须对每个
  接口独立做身份校验"、`07:66`"后端必须……去重并复用最终结果"；
- **manifest 生产方**：`09:27`"未提供清单的后端"——而 manifest 含前端路由模板（`09:119`）。

`04` 把页面 YAML 契约与业务 API 契约全部压在"后端开发者"一个读者上（`04:10-11`）；`00` 术语表
（权威定义）没有任何角色条目；连 `PROJECT_CHARTER.md:52` 变更门禁第 3 问都继承该含糊。下游仓库
按角色拆分（A 团队写 YAML、B 团队实现 API）时，"`04` 约束 A 还是 B"无协议文本可查。

**修复：** 新增 ADR-0038，在 `00` 术语表增加六个角色条目与 §4.1 职责矩阵；全文统一"后端"用词；
`charter` 变更门禁第 3 问改角色化表述。全文替换清单见 ADR-0038 §4（共 21 处）。

### V387（P2）各规范面向读者与角色含糊，缺"契约管谁"总索引

`00` 文档地图有"面向读者"列，但读者≠契约当事方（如"后端开发者"同时被 `04` 和 `07` 列为读者，
而二者契约当事方不同）。下游按角色找契约无总索引。

**修复：** `00` §4.1 职责矩阵（角色 × 产出/遵循/自决），并更新文档地图中
`01`/`02`/`03`/`04`/`07`/`09` 的面向读者列。

### V388（P2）规范强度随校验层级打折（协议已自认）

- `06:26`：`responseMapping` 的 `list`/`total` 规则"校验器**必须**在 L2、L4 **或人工 review** 中
  补充检查"——"必须"落在"或"上，执行点不唯一（对比同文件 `06:38` 的"仅 L2 为权威执行点"）。
- `06:17`：L3a 在 CI 侧"可选前置"，权威拒绝点是 Renderer（fail-closed 合理），但文本未说明
  页面生产方 CI 与 Renderer 的校验责任分配。
- `02` 循环保护"建议 10 轮"与"应停止求值并进入错误态"混排，两个 Renderer 在第 5 轮还是第 10 轮
  失败可观测结果不一致。

**修复：** `06:26` 唯一化执行点并注明"生产方负责保证、Renderer 兜底"的职责；`02` 明确
"实现上限（任意确定值）"与建议值分离。协议自认的"仅 L2（及等价实现）强制；仅跑 L0/L1 的接入方
会漏检"（`03:197`）作为分级机制特征在 ADR-0038 中成文，不再视为缺陷。

### V389（P2）规范行为锚定实现细节词汇

- `01:206-207`：权限行为表用 DOM 表述规范行为（"节点不应存在于 DOM 中"）——非 DOM 渲染器
  （原生、SSR）如何满足无定义。
- `03:136`：`text` 组件"未指定 `valueField` 时取响应体的第一个字段值"——JSON 键序无标准定义
  （详见 V391）。
- `04` §6.1/§6.4：具体中文文案（"系统异常，请稍后重试"等）写在规范性行为表；更新的 `08:383`
  （"如'渲染失败'图标 + 文案"）与 `10:79`（`messageKey` + Host 词典）已把文案划归宿主，边界哲学
  前后不一致。

**修复：** `01` 改为实现无关可观测表述（不渲染且不参与交互 / 只读或禁用呈现）；`04` 错误文案
补注"仅协议安全兜底文案示例，最终展示由 Host i18n 体系决定"，并标记 08 §4.2 / 10 §3.6 为后续
messageKey 化的方向。

### V390（P2）"2.7"版本残留（审计 0080 扫版漏网）

- `01:28` 注释与 `01:47` 正文仍写"当前制品使用 `"2.7"`"/"当前协议版本使用 `"2.7"`"；
- `02:178` 例子 `meta.protocolVersion: "2.7"`（无害，但同批归一）；
- `04` §7 分页表与 `08:286` 协商示例仍写 `"2.0"` 旧版本（保留，标注为历史示例）。

**修复：** `01` 两处改 `"2.8"`；`02` §9.2.2 的 `"2.7"` 与 `04` §7、`08` 协商示例确认为有意
的版本下限/历史示例，不修改（防漂移原则：历史示例保留原版本文本）。

### V391（P3）text 组件默认取值依赖 JSON 键序

`03:136`"未指定 `valueField` 时取响应体的第一个字段值"。JSON 键序无标准定义，两个 Renderer 对同一
响应可能取到不同字段。本轮**不修改**（改默认语义属 MINOR），登记为候选：后续 ADR 将默认取值改为
"响应体若恰有一个字段则取该字段，否则返回 `COMPONENT_DATA_TYPE_MISMATCH`"。

### V392（P3）UI 文案跨 Renderer 逐字一致性要求

`04` §6.1/§6.4 的具体中文文案是规范行为表内唯一要求逐字一致的呈现层义务，与 08 §4.2 / 10 §3.6 的
Host 词典化边界哲学不一致。本轮先补注边界；彻底 messageKey 化登记为后续 ADR 候选。

### V393（P3）既有建议/默认措辞与 MUST/SHOULD 体系不一致

- `02:116` §8 标题"校验建议"承载"禁止 eval/new Function"等实质硬约束（建议节内嵌强制）；
- `07:68` "Renderer 默认使用 toast 展示通用成功/失败提示"无 MUST 级语句锚定；
- `10:343` "HTTP-date 由 Host 相对当前时钟换算"以"应"写规范算法。

这些不改可观测结果，跨实现风险低，本轮不动；ADR-0038 §7 登记为后续"效力词汇规范化"候选（引入
RFC 2119 风格 MUST/SHOULD 用法或等价的协议内约定）。

## 与历史审计关系

- **0080/V380**：同为当前线残留，但 0080 只扫了 `conformance/README.md`，本轮补齐核心规范正文
  （V390）。同型残留建议 `release:check` 增加对核心规范"当前协议版本使用"句式的断言（防复发）。
- **0059–0061**（历史校验分层审计）：V388 的"执行点唯一化"延续其"权威执行点唯一"原则。

## 处理顺序与防复发

1. ADR-0038 先落盘（角色命名 + 职责矩阵 + 修订细则），同变更集修订 `00`/`01`/`02`/`03`/`04`/
   `06`/`07`/`08`/`09`/charter；
2. 版本升 PATCH 至 2.8.2（package.json / package-lock / protocol-manifest / MCP / validator /
   README / `00` / CHANGELOG 同提交），MCP DOC_MAP 收录 ADR-0038；
3. 防复发：ADR-0038 之后新契约条款必须写明契约当事方角色；核心规范的版本/年份残留由
   `release:check` 扩展断言覆盖。

## 归档条件

V386–V390 随 ADR-0038 变更集关闭；P3（V391–V393）登记为后续候选不改本轮；门禁（`release:check` /
`check:links` / `validate:conformance`）全绿后归档。
